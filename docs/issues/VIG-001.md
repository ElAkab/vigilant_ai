# VIG-001 · Correction du compteur d'articles & rationalisation de la pagination

**Priorité :** 🔴 Bloquant | **Phase :** 1 | **Type :** Bug + Refactor  
**Date création :** 2026-06-01 | **NMU :** Non commencé

---

## 🐛 Problème

Le compteur d'articles affiché dans le header affiche **80 articles disponibles**, mais l'utilisateur ne peut en parcourir qu'une fraction via la pagination (5 par page). Incohérence entre le nombre affiché et le nombre réellement accessible.

## 🔍 Analyse technique

### Flux de données actuel

```
RSS Sources (4) → fetchRssArticles() → merge TOUS les articles
  → dedupeAndSort() → merged (peut contenir 80+ articles)
  → slice(0, limit) → renvoie max 60 articles au client
  → Client: pagination locale pageSize=5
```

### Code concerné

| Fichier | Ligne | Rôle |
|---|---|---|
| `server/routes/articles.ts` | 53-60 | Merge all, slice to `limit` (default 60) |
| `server/lib/rss.ts` | 11 | `dedupeAndSort()` — dédoublonne par `urlSource` (pas par `id`) |
| `src/services/articlesService.ts` | 12 | Hardcode `?limit=60` |
| `src/pages/ArticlesPage.tsx` | 15 | `pageSize = 5` |
| `src/pages/ArticlesPage.tsx` | 84 | Compteur : `{loading ? '…' : items.length}` |

### Hypothèses sur la cause

1. **Limite non respectée** — le `slice(0, limit)` fonctionne, mais si 80 articles existent, le compteur affiche le résultat du slice (60 ou 80 selon si le paramètre est bien passé)
2. **Dédoublonnage par URL** — `dedupeAndSort()` utilise `map.set(item.urlSource, item)` : si deux articles différents ont la même URL source (ex: page d'accueil du Monde), un seul est conservé. Bug potentiel de perte de données.
3. **Cache TTL 10 min** — les articles sont cachés 10 minutes côté serveur. Un refresh peut afficher un stale count.

## 🎯 Options possibles

### Option A — Pagination côté serveur (recommandée)

**Principe :** Le serveur ne renvoie que la page demandée + le `total` d'articles disponibles.

```
GET /api/articles?limit=10&offset=20
→ { items: Article[], total: 80, page: 3, totalPages: 8 }
```

| ✅ Avantages | ❌ Inconvénients |
|---|---|
| Compteur toujours exact (le serveur connaît le total) | Refactor du endpoint API |
| Passe à l'échelle (1000+ articles) | Le client doit gérer `total` séparément de `items` |
| Pas de chargement inutile (seulement 10 articles par requête) | Un appel API par changement de page |
| Cohérent avec les bonnes pratiques REST | |

**Impact :** Modifier `handleListArticles` pour accepter `offset`, renvoyer `total` non tronqué.

---

### Option B — Pagination locale avec pageSize augmenté

**Principe :** Garder le chargement de 60 articles, mais passer `pageSize` de 5 à 10 ou 15.

| ✅ Avantages | ❌ Inconvénients |
|---|---|
| Changement minimal (1 constante) | 60 articles chargés en mémoire même si on n'en voit que 10 |
| Pas de refactor API | Le compteur reste faux si >60 articles existent |
| Navigation plus fluide (moins de pages) | Ne résout pas le problème de fond |

**Impact :** Modifier uniquement `pageSize` dans `ArticlesPage.tsx`.

---

### Option C — Compteur corrigé + limite cohérente

**Principe :** Le serveur renvoie le `total` réel (sans limite) + les `items` limités. Le compteur affiche le `total`. On choisit une limite raisonnable (ex: 100).

```
GET /api/articles?limit=100
→ { items: Article[100], total: 80, meta: { ... } }
```

| ✅ Avantages | ❌ Inconvénients |
|---|---|
| Compteur exact | Le `total` nécessite de compter avant le slice |
| Limite cohérente (100 articles = ~16 pages à 6/p, ~10 pages à 10/p) | 100 articles chargés en mémoire |
| Changement modéré (ajout d'un champ dans la réponse) | |

**Impact :** Modifier `handleListArticles` pour renvoyer `total: merged.length`, ajuster le client.

---

### Option D — Scroll infini (infinite scroll)

**Principe :** Remplacer la pagination par un scroll infini avec chargement par lots.

| ✅ Avantages | ❌ Inconvénients |
|---|---|
| UX moderne, pas de clics | Refactor lourd du composant ArticlesPage |
| Charge progressive | Complexité de gestion d'état |
| | Moins adapté à un dashboard de veille (on veut savoir où on en est) |

---

## 📊 Recommandation

**Option A (pagination serveur)** avec `pageSize=10` est la solution la plus robuste :

- Le compteur reflète le **total réel** (pas de mismatch)
- Performance optimale quelle que soit la volumétrie future
- Architecture propre : le client ne charge que ce qu'il affiche
- `total` permet d'afficher "Article 1-10 sur 80"

---

## 🧪 Critères de validation

- [ ] Le compteur affiche le nombre exact d'articles disponibles
- [ ] La pagination permet d'accéder à TOUS les articles
- [ ] Le `pageSize` est configurable (constante unique)
- [ ] Le `dedupeAndSort()` dédoublonne par `id` ET `urlSource` (pas seulement `urlSource`)
- [ ] Aucune régression sur le temps de chargement initial
